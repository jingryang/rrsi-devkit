# 相关算子检索与筛选

为用户指定的目标算子寻找具有参考价值的候选算子。以实际文档、测试与源码为依据，先验证硬性要求，再按功能、tiling 模板策略、调优策略的相似性排序。

## 输入

从用户请求、`$ARGUMENTS` 或当前会话中提取以下参数。参数格式不限，支持自然语言或键值形式。

| 参数 | 必需性 | 说明 |
|---|---|---|
| `target_path` | 必需 | 目标算子目录 |
| `search_roots` | 必需 | 一个或多个检索根目录 |
| `target_name` | 可选 | 未提供时从目标目录及接口定义推断 |
| `top_k` | 可选 | 最终详细展示数量；未提供时展示全部满足硬性要求的候选 |
| `output_path` | 可选 | Markdown 报告保存路径；未提供时直接在回复中输出 |
| `focus` | 可选 | 优先关注的场景、芯片、dtype、layout 或实现策略 |

输入示例（仅示意参数形式，不是默认值）：

```text
/related-operator-discovery target_path=<目标算子目录> search_roots=<检索目录一>,<检索目录二> top_k=5
```

必需参数缺失且无法从上下文确定时，一次性询问缺失项。不要固化任何示例算子名称、路径、算子类别或芯片型号。

开始前验证路径存在且可读。检索限于 `search_roots`，允许读取 `target_path` 以建立对照；共享代码或外部 golden 位于范围外时，记录引用，必要时询问是否扩大读取范围。不要自动扩大候选检索范围。

## 硬性筛选要求

只有以下四项均经证据验证为“通过”的候选才能进入最终推荐。未知、缺失或不满足均不能作为通过处理。

| 要求 | 通过标准 | 不足以通过的情况 |
|---|---|---|
| 与目标公式不完全一致 | 对输入、输出、计算表达式及参数语义做对照，指出实际数学计算或聚合规则的差异 | 仅名称、维度数、dtype、layout、接口、硬件或实现方式不同；同一公式的等价改写 |
| 文档详细 | 有可读取的实质文档，足以说明计算语义、输入输出、关键参数与限制；列出覆盖内容及必要缺口 | 仅空文档、标题、接口名或笼统介绍；仅凭存在 `docs/` 判定 |
| 有 ST 测试且包含 golden | 定位系统测试入口、用例以及实际使用的 golden/参考实现，并追踪调用或配置关系 | 只有 UT、只有测试目录、未使用的 golden 文件，或无法追溯的外部引用 |
| kernel 和 tiling 代码完备 | 能追踪 host tiling 到 kernel 的对应实现，包含实际计算、分支选择与必要数据结构，关键依赖可解析 | 空壳、TODO、仅注册信息、缺失的关键头文件或无法追踪的主要实现 |

补充判定规则：

- `docs/`、`tests/`、`op_host/`、`op_kernel/` 是常见线索，不是强制目录名称。接受仓库约定的等效布局。
- golden 可以是测试内公式、框架参考实现或共享模块，但必须追踪到实际计算及测试调用。测试调用与被测接口相同的实现，不能直接视为独立 golden。
- 共享 kernel/tiling 或公共 golden 可以算作完整实现的组成部分，前提是能解析并读取对应依赖。不要因代码复用直接排除。
- “实现完备”是静态证据结论，不等同于已编译或运行验证。
- 两个公式仅通过重命名、索引变换或代数改写即可一致时，视为公式完全一致。若差异仅在维数、参数范围、边界约定等方面，需进一步证明它改变实际计算语义；不能证明则标为待核实。
- 非计算类算子也要比较输入输出映射或操作语义，不能因没有显式数学公式就自动通过。

## 执行流程

### 1. 建立目标算子画像

阅读目标的接口/设计文档、tiling、kernel 及必要测试，记录：

- 功能：输入输出、公式或操作语义、聚合/归约方式、窗口或索引规则、边界处理、支持场景。
- tiling：分核维度、任务映射、分块维度、UB/其他片上存储预算、主块尾块处理、tiling key/模板分支及选择条件。
- 调优：数据布局与搬运、对齐、向量化、buffer 复用/双缓冲、流水同步、数据复用、特殊 shape 路径和硬件约束。

每项记录来源。缺少目标信息时明确标注哪些比较无法完成，不自行补造公式或策略。

### 2. 枚举并初筛候选

1. 对检索根目录去重，按仓库实际结构枚举算子目录，排除目标目录本身及指向同一目录的别名。
2. 先根据算子类别、文档语义、接口和实现关键词建立候选集。不要只匹配目标名称；也要考虑名称不同但归约、分块或数据流相似的算子。
3. 检查候选的文档、ST/golden、kernel 和 tiling 入口；对明显缺失的候选记录排除原因。
4. 按需读取相关文件，先获取结构和索引，再定向读取源码，避免把整个仓库无差别载入上下文。

仓库存在可用代码索引时可优先利用索引导航；否则使用 Glob/Grep 和 Read。使用 Bash 时仅执行必要的只读检索命令。不要安装依赖、编译或运行算子测试。

### 3. 逐项核实硬性条件

对初筛候选建立证据表，依次验证公式差异、文档、ST/golden 和代码完整性。

对于公式，写出目标与候选的表达式或明确操作规则，并说明关键差异。文档公式与 golden/kernel 不一致时，列出冲突位置，标为待核实，不进入最终推荐。

对于测试，追踪“ST 入口 → 用例配置/数据 → golden → 比较检查”的链路；区分静态确认存在的测试与实际运行通过的测试。

对于实现，追踪“tiling 入口 → 参数/模板或 key 选择 → kernel 入口 → 实际计算实现”的链路。模板类、头文件实现、公共函数均应追踪到关键逻辑。

对已确定不通过的候选可停止后续深读；未检查项标为“未检查”，不要伪造完整验证结论。

### 4. 分析三个相似性维度并排序

对通过全部硬性条件的候选，分别给出“高/中/低”相似性及证据：

| 维度 | 重点比较 |
|---|---|
| 功能 | 运算类别、输入输出关系、归约轴、窗口/索引结构、边界处理及适用场景 |
| tiling 模板策略 | 分核与分块映射、存储预算、模板/tiling key 选择条件、主尾块策略；说明可对应的实际分支 |
| 调优策略 | 搬运与计算瓶颈、数据复用、向量化、对齐、缓冲与流水、特殊 shape 优化；说明具体机制 |

“高”表示关键机制直接对应，“中”表示部分机制对应但需要改造，“低”表示仅有弱关联或一般性共性。未知应写“证据不足”，不能假定为相似。

综合排序优先考虑三个维度都有明确关联的候选，再结合用户 `focus` 评估实际借鉴价值。同等情况下优先功能和 tiling 更接近、证据更完整者。仅共同使用常见 API、同属一个目录或具有相同模板名称，不能作为高度相似的充分证据。

不要把“都用了双缓冲”等泛化描述当作完整分析；说明缓冲对象、触发条件、解决的瓶颈及与目标的对应关系。为每个候选说明可借鉴点及迁移限制。

所有决定性结论必须提供可定位证据，优先使用 `文件路径:行号` 并附符号名；行号必须来自实际读取，不得猜测。

若设置 `top_k`，仅限制详细推荐的展示数量，报告通过筛选的总数及其余通过候选的名称；不要为凑数量降低标准。若未找到满足全部要求的候选，明确说明，并列出排除或待核实原因。

只有完成全部根目录的候选枚举和必要筛查后才能声称完整覆盖。检索受限时，说明已覆盖和未覆盖范围，避免宣称“没有其他相关算子”。

提供 `output_path` 时将报告写入该路径；路径已有文件时先检查，避免覆盖用户内容，必要时另存新文件并告知实际路径。否则直接返回报告，不额外创建报告文件。

## 执行约束

- 本技能默认执行静态检索与分析，不修改目标和候选算子的源码、文档或测试。
- 不自动生成替代文档、补写测试或实现来使候选满足硬性条件。
- 不将文件/目录存在等同于内容合格，不将源码分析等同于运行验证。
- 未读取的内容不作为证据，不推测性能收益；性能结论需区分源码意图和实测数据。
