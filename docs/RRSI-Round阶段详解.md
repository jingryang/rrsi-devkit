## 1. 一句话 + 在全局中的位置

> **每一轮：给当前最好的 harness 出两个改进版，让它们和冠军在同样的任务
> 上各比一场，谁分数高且「赢得干净」，谁当新冠军。重复 20 轮。**

前两个阶段是赛前准备：baseline 测出起点分 S₀，calibrate 测出噪声带 δ。
round 是唯一真正「进化」的阶段——它消费 (S₀, δ) 这两把尺子，每跑一轮
harness 才有机会真的变好一次，并把结果写回档案供下一轮使用。

## 2. 一轮的完整故事

把进化想象成一场**擂台赛**，冠军是当前 harness，一轮 = 一场卫冕战：

> 早上，**教练**调出冠军最近的比赛录像——只看输得最惨的几场和赢得最漂亮
> 的几场，总结「弱在哪、强在哪不能丢」（**①复盘**）。
>
> 然后翻两份资料：**赛程表**——前期一份方案可以打包改 4 处，越到后期一次
> 只许改 1 处，赢了输了都清楚是谁的功劳（**②预算**）；**病历本**——用过
> 哪些招、疗效如何。没用的招不许再开原方；连续几轮无起色的药直接停；
> 冠军连着几轮没长进的话，这轮必须留一个名额给「从没试过的招」
> （**③查病历**）。
>
> 两位**军师**互相不认识、各写各的方案，并直接在各自的**沙盘**（工作副本）
> 上把改动做出来——不对真身动手（**④出策**）。
>
> 方案先别急着上台。**审查官**查两件事：有没有偷看考卷（读评测器）、
> 有没有背答案（把考题编进 harness）——查出打回重写，最多 5 次；过了
> 审查还要**体检**：真跑一遍，跑不起来的直接淘汰（**④审查+体检**）。
>
> 幸存者上**真擂台**：全部训练任务上各打 2 场，机器打分（**⑤评测**——
> 全流程最贵的一步）。
>
> **裁判**持三条规则裁决（**⑥**）：不许比历史最好成绩差出一个噪声带；
> 赢的幅度要配得上多花的 token；胜利必须干净——靠少交卷换来的分判负。
>
> 够格者中分最高的**登基**（git 分支快进到他）；一个都不够格，冠军
> **连任**——守住了底线本身就是结果（**⑦传位**）。
>
> 明天，教练看的就是新王的录像了。

## 3. 七步详解

每步先一句故事，再给真实机制。

### ① 复盘 —— Analyze(H_t, D)

**机制**：从冠军上次评测的存档（`jobs/<job>/eval.json`）挑出**最差 22 个
任务的最差 trial** + **最好 6 个任务的最好 trial**（后者是「成功习惯」，
后续改动不许破坏的行为基线），交给 analyst（LLM）产出 `failure_modes`
（失败模式排行）与 `success_habits` → `r{t}/analysis_report.json`；
跨轮汇总存 `global_analysis.json` 作先验。文件已存在则直接复用（resume）。

**为什么**：SKILL.md 的铁律——**机制必须配对失败类别**：编译失败该改
API 查询纪律，精度失败查尾块/同步/累加精度，性能不足才轮到 tiling/流水。
配错类别的改动，测出来只是噪声。

### ② 预算 —— 退火编辑预算 b_t

```
b_t = ceil( b_min + (b_max−b_min)·½(1+cos(πt/T)) )      # 默认 4 → 1
```

**为什么退火**：早期对 harness 了解最少，允许一份方案捆绑 4 个协同改动
快速试错；晚期 b_t=1，一轮一个变量，测量结果**精确归因到单个组件**，
历史记录随之变成干净的因果证据。

### ③ 查病历 —— σ_t / T_t / U_t / B_t

从编辑历史算出四个量，写入 `r{t}/directives.json`：

| 量 | 含义 | 计算 |
|---|---|---|
| `σ_t` 停滞标志 | 冠军最近 3 轮没动静？ | `S_t − S_{t−3} ≤ δ` |
| `T_t` 试过集合 | 出场且被实测过的组件 | 有实测编辑的组件 |
| `U_t` 未试集合 | 从没出场过的组件 | 9 类 − T_t |
| `B_t` 剪枝集合 | 近 4 轮最好成绩 ≤ 0 的组件（附其已上身机制清单） | `g_t(l) ≤ 0` |

三条衍生规则：

1. **不许重复吃断头药**：被实测否决的机制不得原样重提（军师读得到完整历史）；
2. **探索槽位**：σ_t=1 且有未试组件时，本轮末位变体被**强制**至少改一个
   新组件——守不守由 critic 按 diff 验收（`loop.py:523`）；
3. **停药也是处方**：删掉 B_t 组件积累的机制本身就是合法编辑——进化
   不只加东西，减东西同样重要（红线：安全机制不许光删不换）。

### ④ 出策 —— 每个变体 V ∈ {A, B} 的完整子流程

```
沙盘   git worktree add wt/r{t}V（分支 ascendc-devkit/r{t}V，整仓检出）
  ↓
出策   proposer（LLM）读：复盘报告+病历+两部宪法(SKILL.md/PATTERNS.md)
       +指令(b_t/σ_t/U_t/B_t)+成败轨迹+自己的预测命中率记分板
       → 直接改沙盘文件，输出 edits[{component, hypothesis, predicted_affected}]
       两条硬纪律：
       · Retroactive check：有此机制哪些失败会好转/会不会破坏成功/为何能迁移
       · Predictions：点名预期涨分的任务——评测后对答案，乱许愿记过
  ↓
审查   critic：正则 denylist（改 bench/路径逃逸/写死分数/指向运行产物）
       + LLM 审查，抓两类作弊：
       · 偷看考卷：读评测器内部、硬编码只有评测器知道的阈值
       · 背答案：按算子名/level 分支、把基准分布编成 API 清单
       不合格 → 带理由打回军师重写，最多 repair_rounds=5 次
  ↓
标签   提案声称改 X 组件、diff 实际是 Y → 按 diff 强制改标签（归因以实为准）
  ↓
提交   commit 到候选分支（冠军身份始终是 commit）
  ↓
体检   smoke（只查存活，不判胜负）：compileall → import 关键入口
       → 真跑 1 个冒烟任务 → missing=0 且 valid_rate>0 才放行
```

被拒的变体（`critic_reject`/`smoke_fail`/`no_proposal`）**零评测成本**
出局——审查放在评测前，就是为了把脏候选挡在花钱之前。

### ⑤ 评测 —— Evaluate(H′, 全集, k)

通过筛选的候选**并行**评测（线程池，`eval_parallel`）：完整训练集 ×
k=2 trials，走 `bench/run_tasks.py` 发车（CANN 环境 + NPU 卡 + DevKit
batch），单 trial 上限 4 小时、每任务最多 3 次尝试。语义与 baseline 完全
一致，两条保护：

- **missing**（infra 失败）> 15% → 自动重试一次，仍超 → `eval_invalid`
  不进裁决（环境坏了不算候选的错，也不给分）；
- **present-zero**：编译/精度失败是能力问题，reward=0 但有 verdict——
  候选无法靠把 trial 搞挂美化自己。

### ⑥ 裁决 —— 三道门（详见 §4）

`selection.py`（纯函数）逐候选检查三条规则 + 领域 guards；裁决写
`r{t}/decisions.json`，每条编辑追加 `history.jsonl`，预测命中率写
`attribution.jsonl`。

### ⑦ 传位

```
有够格者 → S′ 最高者上位：git fast-forward evolve/ascendc-devkit
          frontier 更新 incumbent={t+1, 新commit, S′}，S* = max(S*, S′)
无人够格 → 冠军连任 H_{t+1} = H_t（保守拒绝是规则一的设计目的，非失败）
```

无论哪种：trajectory 追加第 t+1 项（本轮 settled）、**候选分支保留**在
git 里（沙盘删除）、下一轮从新冠军重新开始。20 轮跑完 `run` 结束；
`touch runs/ascendc-devkit/STOP` 可在当前轮结束后叫停。

## 4. 裁判的三条规则

对每个候选（S′, C′），ΔS = S′ − S_t，ΔC = (C′−C_t)/C_t：

```
门1 噪声底线   S′ ≥ S* − δ
     锚在「历史最高分」（只增不减）→ 变差的候选靠运气也上不了位，
     「每轮小跌但看起来没跌」的下山扶梯被焊死。

门2 成本规则   ΔS > δ（真赢）：  ΔC ≤ β0 + β1·ΔS      （β0=0.10, β1=40）
               即：+1pp 得分最多换 +40% token，另有 10% 免费额度
               ΔS ≤ δ（假赢）：  100·ΔS − 15·ΔC + 0.5·ν > 0
               ν = novelty：结构性组件（skill/memory/client_tool/subagent）
               中冠军从未赢过的种类数——噪声内的波动必须靠探索新结构才放行

门3 guards（一票否决，与冠军比，总分再高也没用）：
     missing率 ↑ ≤ 0.10 ｜ no-submission率 ↑ ≤ 0.20
     valid率   ↓ ≤ 0.10 ｜ pass率      ↓ ≤ 0.10
```

三条合起来回答一个问题：**这个候选是「真的更好」还是「噪声 + 摆烂 +
运气」？** 全过才叫 admissible，admissible 中 S′ 最大者上位。

## 5. 组件词表

每条改动必须归入 9 类之一（标签由 critic 对照 diff 强制校验）：

```
prompt ｜ control_flow ｜ config ｜ output_plumbing ｜ context_mgmt
｜ client_tool ｜ skill ｜ memory ｜ subagent
```

它是整个记账系统的原子单位：病历本按组件记疗效、U_t/B_t 按组件算探索
与剪枝、novelty 按组件计新意、b_t 退火保证后期一轮一个组件。

## 6. 产物增量

相对 baseline+calibrate 完成后的状态，一轮新增：

```
runs/ascendc-devkit/
├── r{t}/                      ← 本轮决策现场（⭐ resume 依赖）
│   ├── analysis_report.json   ← ①复盘（已存在则复用）
│   ├── directives.json        ← ②③ b_t、σ_t、探索/剪枝指令
│   ├── decisions.json         ← ⑥逐候选裁决
│   └── A/ B/                  ← ④⑤ 每变体：proposal.json(+修复轮)
│                                 diff.patch、critic.json、smoke.json、
│                                 prep.json(commit/分支)、eval.json
├── jobs/r{t}V/...             ← 候选评测原始产物（同 base 结构）
├── jobs/r{t}V_smoke/...       ← 冒烟（每轮删除重跑）
├── wt/r{t}V/                  ← 沙盘（轮末删除；崩溃时保留供续跑）
├── logs/r{t}.log, r{t}V.log   ← driver 与评测日志
├── frontier.json              ← 更新：incumbent 推进/原地，trajectory+1
├── history.jsonl              ← ⭐ 追加：每条编辑一行
└── attribution.jsonl          ← ⭐ 追加：每条编辑的预测命中率
```

与 calibrate「只加一个文件」相反，round 是产物最密集的阶段——每个 LLM
决策、每次评测、每条裁决都有落盘对应物，全程可审计、可断点续跑。

## 7. 轮间积累

| 积累物 | 通俗含义 | 如何影响下一轮 |
|---|---|---|
| trajectory | 冠军战绩曲线 | σ_t 停滞判定从这里读 |
| history.jsonl | 病历本 | 不重复吃断头药；b_t=1 后记录即单组件因果证据 |
| attribution.jsonl | 军师的对答案本（近 20 条） | 回流给军师，过度声称记过 |
| global_analysis.json | 跨轮诊断汇总 | 下轮复盘的先验 |
| evolve 分支 commit 链 | 冠军族谱 | 每轮候选从当前冠军分叉，winner 是直系后代 |

**整体设计**：b_t 从 4 退到 1，20 轮构成一次「先发散、后收敛」的搜索——
早期买广度（一轮一组组合拳），后期买纯度（一轮一个变量）。

## 8. 常见疑问

**Q：两个改进版会互相抄吗？**
不会。隔离沙盘、同样情报、互不知道对方——一轮买两次独立机会。

**Q：一轮最多花多少评测？**
2 候选 × 任务数 × k。当前 1 任务时约 2~4 个 trial；六算子 split × k=2
时是 24 个/轮。墙钟时间主要由评测决定（单 trial 上限 4h）。

**Q：critic 打回后是谁在改？**
还是军师自己，带着审查理由重写，最多 5 次——考官划问题，考生限期改。

**Q：中途崩了怎么办？**
各步产物落盘即复用：复盘报告在 → 跳过①；prep.json 在 → 复用已提交
候选；eval.json 在 → 跳过评测。重跑同一命令从断点继续。driver 另有保护：
连续 3 轮没 settled 自动停机（`driver.py:44`），防止坏环境烧光预算。

**Q：冠军连任是不是浪费了一轮？**
花了评测钱，但没浪费状态：两个候选被拒的原因全进病历，负面证据引导
下轮换方向（或触发探索槽位）。

**Q：改进版可以删功能吗？**
可以甚至鼓励（剪枝集 B_t 就是干这个的）。红线只有一条：安全机制
（编译门、部署冒烟、精度回环、知识库查询、看门狗）不许光删不换。

**Q：军师知道考题吗？**
知道——训练集需求包是合法输入，随便读。但**不许编码**：按算子名分支、
硬编码答案/阈值都算作弊，critic 会打回。检验标准只有一条：换个陌生
算子这改动还成立吗？

**Q：怎么只跑一轮看看？**
`round --t 0 --dry-run`：只做①~③（复盘+指令），停在出策前；去掉
`--dry-run` 完整跑一轮。
