# 模式库：参考依据，而非候选清单

本文面向基于阶段图的算子生成平台，归纳各类机制通常采取的形态，以及目前已知的结论。

**这不是一份供人逐项挑选的清单。** 它只做两件事：避免重复探索已评估过的方向；说明每一类机制的实际形态。提出本文件没有、但有证据支持的新机制，是更受期待的结果。

每项建议都必须通过 `SKILL.md` 的核心检验：

> 它能否帮助一名合格的 AscendC 算子开发者，更高效地处理大量陌生算子？

# 第一部分：平台机制模式

## 1. 阶段图与编排机制

平台不是简单循环，而是由 `GraphExecutor` 遍历的 `StageNode` 树。阶段之间有门禁，纠错/升级结果上有作用域受限的回环。

这也产生了一整类提示词改不动的控制流故障：

- 门禁中止了一次已经产出可部署算子的运行；
- 回环条件读错字段，回环永远不会触发；
- 分支汇合时丢了子节点状态；
- 阶段在所需输入产物尚不存在时启动，在空输入上继续跑；
- 纠错重试重跑了昂贵阶段，而真正出错的是更便宜的阶段。

这类问题最能说明**机制修改通常比文字修改更有效**：故障在阶段连线里，不在策略模型的知识里。提方案前先看事件日志和状态快照，确认是哪个阶段、哪条边、哪个门禁决定了结果。

### 1.1 实际阶段链

`README`/`SKILL.md` 里的九阶段是名义划分。本实例的 trial 实际跑的是 `self_evolve_op`（`scripts/batch_self_evolve.sh` 生成的 manifest 里 `workflow: self_evolve_op`）：

    entry -> context -> requirement -> [general-design | detailed-design]
          -> test_design -> codegen_init -> codegen -> precision_debug
          -> cannbench_adapt -> cannbench_eval -> finalize

`generate_ascendc` 是另一条工作流，尾段是 `perf -> integrate -> finalize`；trial 不跑 `perf` 和 `integrate`。

真实运行里，`report.json` 记录的节点名是完整路径，可以直接看出复合阶段展开了什么：

    self_evolve_op/requirement/requirement
    self_evolve_op/general-design/general-design-generator/general-design-generator
    self_evolve_op/detailed-design/{dd-intake, template-division, tiling/<T>/tiling, synthesize, docgen}
    self_evolve_op/ascendc-st-design/ascendc-st-design
    self_evolve_op/codegen_init/codegen_init
    self_evolve_op/codegen/codegen
    self_evolve_op/precision_debug/baseline/baseline
    self_evolve_op/cannbench_adapt/cannbench_adapt
    self_evolve_op/cannbench_eval/cannbench_eval
    self_evolve_op/finalize/finalize

两点值得记住：`test_design` 这一组在报告里以 `ascendc-st-design` 出现；`precision_debug` 下面还能展开 `baseline` 以外的子阶段，只出现 `baseline` 通常意味着精度一次就过。

- **没有 `verify` 阶段。** 精度验证由 `precision_debug` 复合阶段承担。
- **`cannbench_eval` 是一次性评分节点**：跑 `kernel_eval --skip-install`，得到 `overall_score`；它不回环到 `codegen`。
- **`cannbench_adapt` 是封装层的最后一次修正机会**：它做的是仓库胶水适配（例如补 `cann_bench/__init__.py` 的注册、对齐 `m.def` 的参数名）。`LOAD-FAIL` 常常就是靠这一步救回来的。
- `build` / `deploy` / `smoke` 也不在链上：它们是 `codegen` 阶段内 agent 自己跑的 `redeploy` 自修复循环。
- `test_design`（报告里的 `ascendc-st-design`）在 `codegen` 之前定下验收用例；`codegen_init` 做确定性的 section 声明。

引用阶段名时以 `root()` 为准，不要用 README 的示意图。

**避免的做法：随意增加阶段。** 每增加一个阶段，通常就多一次完整 agent 调用。只有能说清楚它会替代哪个现有阶段，或它是产出某项必要产物的唯一合理位置，才考虑新增。

### 1.2 涉及的主要文件

编排骨架在 `src/ascendc_devkit/orchestration/`，运行装配与入口在 `application/`、`cli/`。路径均以 `third_party/AscendC-DevKit` 为根。

- `workflow.py`：工作流声明、`Workflow.validate_chain()`、`GenerateAscendCWorkflow`、`TRANSITION_TABLE`（corrective / escalation / validation 三类路由）。
- `graph_executor.py`：节点树遍历、阶段执行、门禁求值、回环路由、并行调度。
- `node.py`、`node_forkjoin.py`、`node_sidetask.py`：`StageNode` / `AtomicStage` / `SequentialGroup` / `ForkJoinGroup` / `SideTask` 与合并检查。
- `kernel/`：`gate.py`（`Gate` / `GateResult`）、`action.py`、`event.py`、`runner.py`、`state.py`。
- `registry.py`：`STAGE_REGISTRY` / `WORKFLOW_REGISTRY` 与懒加载。
- `stages/`：各阶段实现；跨阶段复用的门禁在 `stages/gates.py`（如 `BuildInRepoGate`）。
- `design_tree.py`、`precision_debug_tree.py`：两个 `CompositeGroup` 的子树组装，子阶段在 `stages/design_substages.py`、`stages/precision_debug_substages.py`。
- `exec_context.py` / `run_context.py`：单次节点执行上下文 / 运行级不变量（目标硬件、实测与软件环境）。
- `artifact_recovery.py`、`issue_render.py`：产物缺失恢复、门禁阻塞问题的确定性渲染。
- `domain/contract.py`：`StageIOContract`，`validate_chain()` 的检查对象。
- `application/dispatcher.py`、`resume_resolver.py`、`run_packaging.py`：分发、续跑、产物打包。
- `cli/commands/run.py`、`stage.py`、`show.py`：运行、单阶段运行、查看。

模型侧指导不在编排代码里：`.claude/agents/*.md`、`.claude/skills/*/SKILL.md`、`.claude/rules/` 由 `capabilities/` 层加载后注入阶段。它们影响"阶段内部做什么"，不影响"阶段之间如何连线"。

### 1.3 运行时产物

一次运行在 `output/<batch>/<execution>/` 下留下这些证据，分析和诊断都从这里取：

| 产物 | 内容 |
|---|---|
| `report.json` / `report.md` | 实际执行过的节点表：完整节点名、status、迭代次数、耗时。判断"跑没跑、卡在哪、哪一步最贵"以它为准 |
| `events.jsonl` | 事件流：`stage_enter` / `stage_complete` / `iteration_*` / `action_*` / `forkjoin_*` / `infra_backoff` / `env_warning` / `run_resumed` |
| `state_snapshot.json` | 运行终态：`eval_result`（四轴分数与用例数）、`debug_result`（本地精度回环）、`deploy_result`（含 `smoke_passed`）、`adapt_result`（封装层改了哪些文件），以及 `codegen_*_retries`、`*_same_error_streak`、`codegen_consecutive_failures` 等重试/停滞计数 |
| `agents/<agent>-NN.jsonl` | **每次 agent 调用一个文件**，每行 `{turn, role, blocks[]}`，block 类型有 `text` / `thinking` / `tool_use` / `patch`；整次调用失败时只有一行 `{"type": "crash", "error": ...}` |
| `run.log` | 平台进程的完整输出（可达 MB 级） |
| `subprocess/` | 评测子进程的原始产物，含 cann-bench 评测报告 JSON/HTML/MD |

`report.json` 与 `state_snapshot.json` 是判断结果的两份权威记录；`events.jsonl` 和 `agents/` 是解释"为什么是这个结果"的证据。

## 2. 知识与技能注入

算子知识主要放在 `.claude/skills/<name>/SKILL.md` 和 `.claude/agents/*.md`，不直接写进 Python。技能采用渐进式披露：agent 先只看到名称与描述，需要时再读完整流程。

这适合修**反复出现的错误操作模式**——策略模型一旦知道正确流程就能稳定执行的任务，例如 UB 预算约束下的 Tiling 选择、host 侧 Tiling 契约该提供什么、`aclnn` 封装层的构建顺序。

**纯文字参考类技能，多数收效甚微。** 平台带着二十份这类技能，整体效果可能不升反降。更值得采用的技能至少具备其一：

- 流程具体，且执行结果可检查；
- 附带可执行辅助程序供调用；
- 只在触发条件命中时注入（例如匹配到某类编译错误之后），而非每次运行都注入。

**边界：** 技能正文若只是罗列 AscendC API 名称，或给某个算子族固定配方，那是对基准分布的记忆，不是可迁移方法。合法技能描述**流程**——"调用不熟悉的 API 前，先从知识库索引查签名"——具体 API 内容由 agent 运行时检索。

## 3. 提示词与模板机制

阶段提示词和 agent 定义本身就是指导手段。v0 刻意精简，只描述交付契约，不预置 AscendC 专门知识。

它适用于：模型有能力、控制流也没问题，但不知道**何时、按什么顺序、在什么条件下**行动。

提示词也是效果最不稳定的一类改动。要分清两类改动：**机制性改动**（在特定触发点注入计算得到的上下文或结构化证据）与**激励性重复**（用更多文字反复强调"应该做好"）。通常只有前一类值得花一轮实验。

## 4. 输出管线与产物路由

常见故障：阶段正确完成了工作，下游发现不了、或读不出来。

- Tiling 参数写成了 host 解析器读不了的自然语言；
- Kernel 写进了 `integrate` 不扫描的目录；
- 评测报告放在判定阶段会跳过的运行目录；
- 部署产物已生成，封装层没生成。

只读 agent 的推理过程、不检查真正跨越阶段边界的文件和数据，这类问题往往查不出来。改进方向是明确**阶段间产物契约**，并让下游靠可靠路径发现产物。成本低、行为明确，直接针对 `NO-ARTEFACT` 和 `LOAD-FAIL`。

**通用陷阱：** 把文件搜索扩大到"任意位置找任意报告"，运行会误读先前尝试留下的旧报告，用它给当前尝试评分。产物发现必须限定在**当前这次运行**；有多份时按规则选当前尝试中的最佳，而不是磁盘上第一份。

**成本原则（全文适用）：**

> 在某种成本约束下被否决的机制，不代表它在另一种成本约束下也应被否决。

因 token 或墙钟时间被否，而不是因技术方向错，就仍值得考虑：能否用更小预算实现同方向改进？提新候选时，应指出它相对先前方案改变了哪个成本维度。

## 5. 长运行中的上下文预算

编译与调试阶段会不断积累编译器输出、测试日志、dump 数据。压缩后保留什么，决定了后续阶段还能做什么。

对本平台，后续通常需要：Tiling 参数、封装层必须暴露的接口、`proto.yaml` 的 shape/dtype、当前编译错误的原文。

这些信息是否被保留可从各阶段 transcript 核对。但压缩路径影响每一次长运行；改之前先评估影响面，别为保留少量信息抬高所有运行的成本。

## 6. 解析与格式错误恢复

阶段间传递结构化产物：`proto.yaml`、Tiling JSON、生成的 C++ 文件、封装层注册信息。格式错误会白烧一次 agent 调用，甚至触发整轮回环。

可考虑的机制：给出更具体的纠错提示并附实际解析错误；对接近合法格式的产物做保守修复；让产出该产物的阶段重新生成，而不是重启整条上游链路。

**通用陷阱：** 自动修复结构化产物会改变语义——修好的 Tiling 能通过解析，却可能不再匹配 Kernel 的 `InitBuffer` 尺寸。修复应当保守，有歧义就拒绝；目标是**Kernel 与 host 端约定一致**，不只是让解析器接受输入。

## 7. Tiling 与硬件参数

Tiling 决定后续的分核、UB 占用、tile 形状与尾块处理。反复出现的失败：tile 占用超 UB；核数写成了另一款芯片的数值；shape 不能整除 tile 却没有尾块路径；基地址不满足 32 字节对齐。

v0 没有强制 agent 查询实际硬件参数，也没有要求它用 Tiling 结果核对 Kernel 的 `InitBuffer` 分配。

**不可妥协的边界：不得硬编码硬件参数。** UB 容量、核数、L1/L2 容量、向量宽度都随芯片变化，必须运行时通过硬件查询获得（`PlatformAscendC::GetCoreMemSize`、`GetCoreNumAiv` 一类），再经 compile-info 结构体下发。把当前基准芯片的数值写死，可能在本测试上拿高分、换芯片就失效——这正是分布外评测要暴露的。

三类常量必须分开看，否则检查器会把合法的写成违规、把违规的放过（下面用抽象式子描述，不引用任何一次具体生成的数值）：

1. **芯片容量**（UB/L1/L2 大小、核数、向量宽度）：必须查询，不得写死。
2. **API/协议上限**（例如 `DataCopyPad` 的 `blockCount` 上限）：属于接口约束，可以写成具名常量，但要在注释里说明来源。
3. **软件预留**（同步头、TilingData、TPipe 占用的预留字节）：属于实现选择，可以写成具名常量，但必须从查询到的容量里扣，而不是代替查询。

生成代码里已经见过这两种写法混在一起：把"一次搬运的字节数 ÷ 元素字节宽"这类由硬件常量推出的数值直接写成字面量，属于第 1 类，是潜在的可移植性缺陷；把某个 API 的调用上限写成字面量，属于第 2 类，注明来源即可。检查机制应当能区分这两者，而不是一律报错。

提方案前先从轨迹判断属于哪种：

1. agent 算出了 Tiling，但没检查它与 `InitBuffer` 是否一致；
2. agent 检查了、发现了不匹配，仍然继续跑。

两者需要不同的修复机制。

## 8. 验证门禁：编译、加载与精度

平台可以在评测器真正评测算子之前设自己的门禁，在成本较低的阶段提前发现问题。

只查编译的门禁拦不住 `LOAD-FAIL`；只查能否加载的门禁拦不住 `ACCURACY-MISMATCH`。门禁应覆盖评测器实际检查的关键属性，并使用**算子自身的 golden 和用例**作为验证数据——它们是输入，不是评分器。

**边界：** 门禁可以跑算子自己的 golden 测试，但不能重实现评测器的判定阈值、不能读评测器报告、不能编码只有评测器才知道的通过条件；也不能成为阻止一次运行产出任何产物的唯一屏障。

**中间门禁会与最终评测不一致，这是常态而不是 bug。** 真实运行里出现过：中间阶段的 `deploy_result.smoke_passed = False`，但 `cannbench_adapt` 补上封装层注册后，最终评测报告全部用例通过。原因是冒烟发生在某一次部署尝试，而封装层适配在后面。所以：

- 不要用中间阶段的 smoke 标志代替最终判定；
- 也不要因此认为冒烟门禁没用——它拦的是"部署根本没成功"这类会在后面放大成 `LOAD-FAIL` 的问题；
- 如果要做新的门禁，明确它阻断的是什么，并保证它失败时仍然留下可部署产物（否则会把一次本可通过的运行变成 `NO-ARTEFACT`）。

**读分数时同样要看清语义。** `overall_score` 是几项加权和，其中性能分量在"通过率高但没测到加速比"的算子上会直接是 0，于是总分看起来明显低于同类。所以 `overall_score` 的绝对值不适合跨算子比较，`performance_score = 0` 也不等于"慢"。只有同一算子的前后对比才有意义。

**成本：** 每个算子无条件跑精度门禁，等于无条件付一次真实 NPU 运行。按运行过程触发更经济：冒烟调用没返回输出；精度检查此前已失败过一次。

## 9. 有界的额外策略调用

平台本身已需大量模型调用。对同一个冻结模型做一次有界的额外调用，适合范围狭窄的抽取或选择，例如：

> 输入编译错误和 Kernel 的 Tiling 结构体，只返回不匹配的字段。

不适合开放式推理，也不适合重跑整个任务。**子调用经常得不偿失**：每次调用都增加延迟和 token，而它没有天然的阶段边界证明这笔成本合理。

## 10. 跨算子记忆

平台连续处理多个算子。某类通用问题（尾块缺掩码、某 dtype 分支无法实例化）的经验，对后续算子同样有用。

记忆里只能留**不指向特定实例的通用经验**。条目直接写出算子名、具体 shape 或数值常量，就可能变成对基准集合的记忆化。

**只有写入、没有读取路径的记忆，只是死数据。** 但每次运行都把整个记忆文件塞进上下文，可能比不用更糟。合理做法是按触发条件选择性读取——编译错误签名匹配时注入相关条目。

# 第二部分：算子特征（vector 域）

本部分提炼自 `算子语料评分地图.xlsx` 的 `【领域补充】A5语料评分特征 0814` 工作表，**只保留 vector 域**。

**范围：**

- 保留的族：逐元素、激活、广播、归约、Scan、索引读写、Sort/TopK、池化、归一化、融合、损失函数、优化器、Resize/插值/采样、Shape/排布/拼接、Foreach、Mask/条件/过滤、Cast/类型转换、Random、量化/反量化。
- **不纳入**：Matmul/GEMM/BMM、Convolution、注意力、整层结构、通信/通算融合。这些族围绕矩阵计算单元或跨卡通信组织，与 vector 算子不是同一类问题；它们的结论拿到 vector 算子上会误导。
- vector 族中**当前没有评分证据**的：Scan、Sort/TopK、优化器、Foreach、Random。空白表示**没有证据**，不表示不重要，也不能据此补造特征；同样不要让候选方案的预期收益依赖这些族。

**数据现状（引用前务必核对）：**

- 源表共 24 个算子族、422 条非空记录（223 条正例、199 条反例）；上面第 2 条已说明本文件只取 vector 子集。
- **"影响范围"列不可直接当判据**：422 条里 164 条为空，170 条混入了场景/样例文字（如"vector算子通用反例""逐元素vector算子适用"），仅 88 条干净。判断失败类别要靠特征文本本身，不能靠这一列。
- **K23 量化与 A5 的关系在源表里自相矛盾**：该族 17 条中 14 条标 "A5 强相关 = 否"，另有 3 条标 "是"。因此 K23 的通用量化实现可以引用，但不要把它的具体结论当成 A5 平台的评分依据。

这里保留特征背后的**原因与可迁移流程**，不保留逐算子配方、具名示例或数值常量。

本部分不是另一份机制清单。每个候选仍是一次独立的脚手架改动，以实测通过率评估。

## 11. 七个维度

维度是彼此独立的观察角度，不是每次都要全跑的检查清单。

| 维度 | 主要检查问题 |
|---|---|
| 范式 | 算法是否围绕正确的计算模式组织？实现路线是否在 host/Tiling 阶段选定，而不是运行期不断分支？ |
| 搬运 | 地址计算是否遵循真实存储布局？尾块与非对齐块是否有显式路径？每个操作数是否只搬必要的次数？ |
| buffer | 生命周期是否隔离？缓冲深度是否有生产者/消费者重叠的依据？UB 预算是否按真实 dtype 宽度和查询到的容量算？ |
| 流水 | 搬运、计算、写回能否跨 tile 重叠，还是每段都要等上一段？ |
| 同步 | 每条依赖边是否用了足够且不过量的机制？多次运行结果是否确定？ |
| 计算单元 | 是否用了目标计算单元的高层批量 API？尾块是否掩码？精度需要时是否提升窄 dtype？ |
| 优化 | 核数、tile 大小、模板选择是否由 shape、dtype 和查询到的硬件推导？是否先识别瓶颈再调优？ |

### 使用前的五条边界

**1. 防止基准信息泄漏。** 族级工程原则可迁移（"窗口归约应从输出 tile 反推输入 tile"）；具名算子、逐算子常量、逐算子用例表、"遇到这个算子就做某事"的分支都属于记忆化。源表为说明特征列了算子名，**不要把它们写进代码、提示词或技能**。

**2. 不要把 A5 特性推广到所有芯片。** 这张表是 A5 的快照。声明式计算图调度、寄存器级 SIMD（RegBase/VF）、SIMT/SIMD 拆分、多维 DMA 描述符，都只存在于部分芯片代际。可迁移的是**要问的问题**——"当前平台支持哪些执行模式？不支持时的回退路径是什么？每项容量从哪次运行时查询来？"——不是 A5 的具体答案。

**3. 证据不足时不要补造结论。** 上面六个族空白表示**当前没有评分证据**，不表示它们不重要。别为它们编特征，也别让候选方案的预期收益依赖这些空白。

**4. 不要把性能问题和精度问题混为一谈。** 性能特征不能当精度门禁的依据；精度特征也不能靠"跑得更快"证明修复有效。源表这一列本身不干净（见上），更要按特征文本判断。

**5. 按可检查程度选择机制。**

1. **可机械检查**——只看产物即可判断：Tiling 与 `InitBuffer` 是否一致、声明深度与实际使用是否匹配、有无尾块/padding 路径、是否硬编码容量、未分配工作的核是否提前返回、alloc/free 是否配对、有无标量 get/set 循环。这类检查应落在 `precision_debug` 或客户端工具里，而不是只写进提示词。
2. **需要自测结果**——必须用算子自己的 golden 和用例做有界运行：测不能整除的尾块、非连续输入、重复运行查确定性。用的是算子自己的输入、不用评测器阈值，属工程验证而非作弊。
3. **需要策略判断**——选择哪种模板适合当前 shape、瓶颈在哪、融合边界是否合理。应把计算得到的事实喂给现有阶段，而不是新增一个常驻阶段。

## 12. 七个维度对应的实现模式

每节给的是"该做什么 / 不该做什么 / A5 上对应的机制名"。机制名用于**定位**——知道要动哪个 API、哪个模板、哪个结构体——不是照抄参数的配方。

### 12.1 范式：路线一次选定，固化为编译期分派键

**该做**

- host 侧依据 shape、dtype 和平台能力一次性选路线，把选择编码成模板或 Tiling 键，Kernel 内不再运行期分支。
- 决策要覆盖：计算是否位置局部、有无数据依赖、归约轴能否整体载入片上、哪些轴可广播并可折叠、输出 shape 是否依赖输入数据、是否需要布局重排、量化轴是哪一维、输出长度静态还是动态。
- 每条路线一个独立、可单独测试的模板，Kernel 按键分派。
- **A5 机制：** `IsCapable()` 责任链 + `REGISTER_OPS_TILING_TEMPLATE` 注册多个 tiling 模板，按 shape 规模自动匹配；逐元素类可整体走 DAG 声明式（`DAGSch`/`Bind`）描述 `CopyIn→Compute→CopyOut`，由 `ElewiseBaseTiling::DoTiling<DAG>()` 委托框架管理流水与 buffer，新增同类算子只需替换 compute functor。

**不该做**

- 把彼此独立的元素当成有依赖（在位置局部 Kernel 里引入邻域偏移、累加或坐标映射）。
- 在 Kernel 循环内部展开广播逻辑；把多种策略塞进同一个 Kernel 再按运行期 shape 分支。
- 用字符串或长 `if-else` 在归约模式之间分派；对依赖数据的输出 shape 猜一个最大长度。
- 每个算子族复制一套 Tiling 骨架，不复用基类或模板辅助函数。
- 将本可由 Tiling 预计算的 shape 几何散落在热路径里。
- **语义等价但结构更差的反例：** 多个逐元素激活算子的 `RunTiling()` 结构完全一致却各自维护一份拷贝——任何 bug 修复都要改多处，遗漏风险高。

**平台解读**

这通常说明设计阶段缺产物。设计阶段没输出"shape 类别 → 模板/Tiling 键"路由表，codegen 就会临时拼通用模板，进而精度或尾块处理失败。

路由表与 Kernel 分派都生成后可以机械交叉检查：路由表每条路线都要有对应键，Kernel 每个分支都要对应有效键。

**主要失败类别：** `COMPILE-FAIL`（某分支从未实例化）、`ACCURACY`（选错路线后静默错结果），其次 `UNDER-PERF`。

### 12.2 搬运：遵循真实布局，显式处理尾块，减少重复搬运

**该做**

- 地址计算由真实存储描述符驱动（行/批次 stride、leading dimension），而不是只按逻辑 shape。
- 尾块有专门路径：按实际元素数 padding 或掩码，不读残留数据，不把 padding 写成有效输出。
- 同时提供对齐快速路径与非对齐安全路径。
- 多行/多批数据用循环与 stride 描述符聚合搬运，而不是每行一次调用。
- 对重叠窗口，从输出 tile 反推输入 tile。
- 广播权重、scale 向量、索引表等常驻操作数只搬一次并复用。
- 搬运块足够大以摊薄 DMA 启动开销。
- **A5 机制：** 广播用 `CopyInBrc`，NDDMA 模式下把广播维 stride 置 0，由 DMA 完成数据复用，核内不做展开；多维/带 stride 的搬运用 `DataCopyPad` 的 `blockCount` / `srcStride` / `dstStride` / `LoopMode` 一次描述 shape、stride 与尾块。

**不该做**

- 用"上一块结束地址 + 块大小"推算下一块，忽略 padding 或批次间隔。
- 对非连续张量仍用逻辑 stride 算地址；假设矩阵操作数一定连续。
- 在外层循环里重复搬运常驻操作数；每次外层迭代都重新从 GM 搬广播输入。
- 每行拷一次、每个输出位置拷一次窗口、每个元素调用一次；逐个位置同步写出。
- 片上空间充足仍用碎片化小块：多次小 `DataCopyPad` 处理相邻小段、或 `repeat=1` 分多次调用。
- 对无法摊薄启动开销的小 shape 用高维搬运方案。

**平台解读**

许多反例能直接从生成代码识别：逐行拷贝循环、`prev_offset + len` 一类地址公式、缺 padding 分支、同一循环里反复搬同一 `GlobalTensor` 区间。平台可以机械标记这些可疑模式，再用算子自己的边界用例（不能整除的长度、非连续输入）确认正确性。

但扫描器只能报告可疑，**不能擅自改写地址公式来"修复"寻址**——广播与逻辑 stride 的混淆，正确修法是 host 侧取 `GetStorageShape`/`GetStorageStride` 下发 tilingData，这需要判断，不能机械替换。

**主要失败类别：** 首要是 `ACCURACY`（越界访问、读到旧数据、地址逐块漂移），其次 `UNDER-PERF`。

### 12.3 buffer：生命周期相互隔离，深度由重叠需求决定，预算按实际占用计算

**该做**

- 输入与输出使用各自的队列。
- 需要流式配对的生产者/消费者，用**有依据**的重叠深度；深度 2 是常见起点，不是默认值。依据是"归约/计算开销能否掩盖 MTE2+MTE3"——能掩盖就不必加深，掩盖不了才值得加。
- 常驻操作数用专用区域。**A5 上广播算子 buffer 天然非对称：** 非广播输入开 `TQue` 双缓冲，广播输入用 `TBuf` 单份驻留（不参与流水切换）。
- 按每个 buffer 的元素数与 dtype 字节宽算 UB 占用；对**同时存活**的 buffer 求和，与查询到的容量比较。生命周期不重叠的 buffer 可共享区域（`GetWithOffset` 切分），峰值按同时存活的最大组合算。
- 常量、索引表、掩码向量在 tile 循环外只构建一次。
- 归约 workspace 按参与的核算分配。**A5 机制：** 逐元素类交给 DAG 框架后，`AllocTensor`/`FreeTensor`/`EnQue`/`DeQue` 与双缓冲全部由框架管理（`MemOptCfg<MemLevel::LEVEL_2>`），零配对错误风险。

**不该做**

- 搬入、计算、写出共用同一块 buffer，生命周期冲突。
- 对不变的常驻操作数也用对称缓冲深度——**广播输入开 `TQue` 双缓冲是典型浪费**：两份相同数据，每次迭代切索引，白占一份 UB。
- 每个中间结果各调一次 `InitBuffer`；每个 tile 重新生成常量。
- 某分支（含提前返回或错误路径）alloc 了却没有对应 free。
- 按所有阶段占用之和估峰值，而不是按同时存活的 buffer。
- 假定硬件容量，而不是查询。**A5 RegBase 下尤其注意：** 仍为中间 Cast 各开一整块 float 中转 buffer，会让 UB 占用翻倍，反而挤掉双缓冲空间。

**平台解读**

这是最适合优先做机械检查的类别之一：Tiling 声明的字节数与深度是否与 Kernel 的 `InitBuffer` 一致、每个分支 alloc/free 是否配对、字节数是否考虑 dtype 宽度、每项硬件容量能否追溯到平台查询。检查器应把**首个**不匹配项反馈给产出该结果的阶段，在演变成 `COMPILE-FAIL` 之前修掉。

**主要失败类别：** `COMPILE-FAIL`（UB 超限、队列深度不匹配）、`ACCURACY`（别名覆盖、读到残留），其次 `UNDER-PERF`。

### 12.4 流水：跨 tile 重叠，而不是逐段串行

**该做**

- 深度 2 的队列下，搬运预取 tile (i+1)、计算处理 tile (i)、写出排空 tile (i-1)。
- 内层循环的预取深度有依据，使输入暂存领先于消费。
- 多阶段 Kernel 用环形槽位，容量按实际需求确定。
- 预先启动首个 tile，减少填充空等。
- **A5 机制：** 逐元素类走 DAG + `ElementwiseSch16B` 调度器时，Slot0 搬入/搬出期间 Slot1 正被 Vector 计算，乒乓由框架编排；手写 Kernel 则用 `TQue<VECIN,2>` 与 `TQue<VECOUT,2>` 分属 MTE2/MTE3 两条独立硬件流水线。

**不该做**

- 每个 tile 完成后阻塞等待，再开始下一个；整个张量严格按阶段串行。
- 每个输出位置同步写一次。
- 在 tile 循环内部反复重建队列或推导参数；计算主体含打断指令发射的分支。
- 没有核算重叠槽位所需的容量。

**平台解读**

流水问题主要体现为墙钟差异，除队列深度与执行顺序外，多数难以静态可靠判断，通常要结合性能阶段和 `UNDER-PERF` 轨迹。有用的设计产物是**瓶颈判断与重叠计划**：当前是计算 bound 还是搬运 bound、哪些 buffer 配对可重叠、预取深度怎么定。这样性能阶段不必从头猜。

不要把它变成每次运行都跑的额外测试——对小 shape，即便有优化空间也未必值得多付一次 NPU 调用。

**主要失败类别：** `UNDER-PERF`；复用槽位缺少必要同步时会表现为时序竞争性的 `ACCURACY`。

### 12.5 同步：只保留必要的依赖边，保证确定性

**该做**

- 优先利用队列自身的隐式顺序——这是最容易被忽略的"少做一步"。
- 只有队列顺序覆盖不了的跨 pipe 依赖，才加显式事件。
- 每条数据流用独立事件 ID；ping 与 pong 用不同 ID。
- 全局屏障只用于真正的阶段边界——例如同一数据在读阶段与写阶段之间必须切换时（`PipeBarrier<PIPE_ALL>` 放在**所有** Phase1 写完之后、**所有** Phase2 读之前）。
- 未分配到工作的核在访问内存之前提前返回。
- 标量参数先写完、排好序，再由消费它的 Vector 或搬运单元读取。
- 跨核聚合必须等所有生产者发布结果。
- 各核写互不重叠的区域，结果不依赖调度顺序。
- **A5 RegBase 特别提示：** VF 内对同一块 buffer 的读写需要显式编码先后顺序。

**不该做**

- 每个 tile 边界都上一次全局屏障——把本可重叠的三段强行拉齐，双缓冲收益被抹掉。
- 已有队列顺序时再叠冗余事件。
- **在已关闭自动同步的代码库中依赖自动同步。** 自动同步是主线仓的默认行为，自定义算子仓默认不开——这是高频错误，正确做法是把每条跨 pipe 依赖显式写成 `SetEvent`/`WaitEvent` 对。
- 两个复用同一内存的阶段之间缺屏障；多条并行流共用同一事件 ID。
- 用全局屏障代替本应的点对点握手；生产者完成前就读取聚合偏移。
- 多条数据流同时写入同一队列；`DeQue` 先于 `EnQue`，或队列操作缺配对。
- 跨核原子操作后，无依据地假设 flush/cache 行为正确。

**平台解读**

这张地图明确把确定性视为质量要求。同步问题尤其容易造成"某次通过、下次失败"。

合理的验证范围应当有界：用算子自己的用例少量重复运行并比对，同时检查生成 Kernel 里的依赖边。每次运行都重测会产生真实成本，更适合条件触发——首次精度失败，或检测到多阶段、多核 Kernel。

**主要失败类别：** 间歇性 `ACCURACY`、挂死（在试次层面可能表现为 `NO-ARTEFACT`）、屏障串行化导致的 `UNDER-PERF`。

### 12.6 计算单元：批量 API、尾块掩码、按精度要求提升 dtype

**该做**

- 用目标计算单元的最高层批量 API 表达计算。
- 尾块按实际元素数掩码，不用标量逐个补齐。
- 对 Exp、Div、Log、长累加、统计量等多步计算，先升窄 dtype 到 fp32，最后统一转回。
- 融合连续逐元素链。
- bias、scale、激活、量化等后处理，能由生产者路径顺带完成就不写回 UB 再算一遍。
- 不规则访问用 gather/scatter；索引与地址计算尽量在向量寄存器中完成。
- **有依据的**除法替换：归约/均值类里除数在整块内不变（如 `1/元素数`、`1/总权重`），可在 host 侧 tiling 阶段算好倒数、经 tilingData 传入，Kernel 内用 `Muls` 乘。逐元素除法**不适用**——那里要的是升 fp32 保精度。
- 连续高层 API 之间复用临时 buffer。
- **A5 机制：** `MicroAPI::RegTensor` + `UpdateMask<T>(remainingCount)` 在最后一轮动态屏蔽无效元素；逐元素后处理优先用 Vector 高阶 API（`Silu`/`Swiglu`/`AscendQuant` 等）；per-tensor 常量 scale 走 `SetQuantScalar` 的 Fixpipe 随路通路，不单独派发 Vector 指令。

**不该做**

- 标量 get/set 循环，包括用标量补尾块。
- 对未掩码的尾块直接计算，残留数据参与运算。**A5 RegBase 下，尾块仍用全量 mask 会让有效数据外的随机值参与计算。**
- 低精度 dtype 多步计算没有必要的精度提升（含 Exp/Div 在 fp16/bf16 下直算，导致精度不足或溢出成 ±inf）。
- max/min 用错中性元素；average 类归约的除数语义不一致；有损转换的舍入模式未指定或与要求不符。
- 为改变布局或位宽做不必要的片上往返；逐元素做标量地址计算。
- 重复计算本可由生产者路径顺带完成的后处理。

**平台解读**

一部分可静态检查：标量元素循环、缺尾块掩码、窄 dtype 多步运算。另一部分仍需策略判断。

适合用于核对代码的设计产物是一份简短的**精度与 API 计划**：多步运算用什么 dtype、何处提升与舍入、各阶段用哪类 API、尾块怎么掩码。平台用这份计划检查生成代码，再用算子自己的 golden 验证。

**主要失败类别：** `ACCURACY`，其次 `UNDER-PERF`。

### 12.7 优化：参数由 shape 与硬件推导，先定位瓶颈

**该做**

- 核数由问题规模推导，并设每核最小工作量；尾块是真实剩余量，而不是再分一个完整块；空问题能正确处理，且至少激活一个核。
- 小 shape 路由到少核、数据尽量片上驻留的模板，而不是把少量元素摊到所有核。
- 归约型任务先判断归约轴能否一次全部载入片上。
- 按 shape 类别选模板：全量载入、单轴、多轴、不规则索引、退化情况。
- 倾斜 shape 用负载均衡的切分。
- 避免片上 bank 冲突；控制计算循环规模，使其适合指令发射。
- **A5 机制：** VF（寄存器级）切分要控制大小——单个循环的指令数超过指令队列深度就无法指令双发，IPC 会急剧下降，需要显式 unroll；分核明显不均的 shape 可用 FD 做核间负载均衡；`CeilDiv(a1, numBlocks)` 自适应核数，最后一核用 `a1 - blockFactor × (blockNum-1)` 取真实余量。

**不该做**

- 不论问题规模都固定用物理最大核数，或反过来无依据地强制单核（`SetBlockDim(1)` 等于主动关掉框架的多核能力）。
- 把尾块大小硬编码成固定块因子（`tail = blockFactor` 在不能整除时越界）。
- tile 大小与 shape、平台无关。
- 对搬运 bound 的算子盲目调优计算路径。
- 计算主体过大无法指令双发；访问模式导致 bank 冲突。
- 沿用旧架构的核数、UB bank 结构或 tiling 阈值，未按当前 `PlatformInfo` 重算。

**平台解读**

Tiling 产物可与硬件查询结果、Kernel 自身的 buffer 分配交叉检查；其余优化问题更多依赖性能轨迹。通用规则仍是：没有依据的硬件常量一律不写。只有能从查询到的容量与当前 shape 推导出过程的 tile 大小才是合理配置。

**主要失败类别：** `UNDER-PERF`；尾块处理错误时也会导致 `ACCURACY`。

## 13. 算子族的差异

七个维度通用。族与族的区别在于：**设计时先问什么，以及哪些陷阱反复出现。** 本表只列 vector 族，用于引导设计评审，不是实现配方。

| 算子族 | 设计时先问 | 常见正确性陷阱 | 常见性能陷阱 |
|---|---|---|---|
| 逐元素 | 每个输出是否只依赖同位置，输入输出 shape 是否一致？ | 引入邻域偏移/累加/坐标映射；标量循环 | 单 buffer 致流水串行 |
| 激活 | 位置局部映射，还是含归约段？ | 两段归约间缺阶段边界；无非对齐搬运路径；Exp/Div 未升精度 | 归约段与映射段无法重叠 |
| 广播 | 哪些轴要广播、哪些可折叠？ | 用逻辑 stride 算存储地址；广播维在核内 for 展开 | 对常驻广播输入用对称缓冲 |
| 归约 | 归约轴能否一次全载片上？ | 尾块 padding 污染结果；跨核聚合早于生产者发布 | 各归约单元负载不均 |
| Scan | **本快照无特征** | — | — |
| 索引读写 | 访问是否不规则？索引是数据还是地址？ | 索引未搬完就被读；存储 stride 漂移 | 离散遍历用标量 get/set |
| Sort/TopK | **本快照无特征** | — | — |
| 池化 | 一个窗口能否整体放入片上，还是必须分段流式？ | max 中性元素错误；average 除数语义不一致；大核仍试图整窗搬入 | 每个输出位置单独复制窗口 |
| 归一化 | 归约轴能否整体载入？涉及几个轴？ | 非对齐搬运参数错误；尾块被错误纳入统计量 | 计算 bound 的 shape 上缺指令级重叠 |
| 融合 | 哪些中间值无需写回 GM？ | 中间结果反复过 GM；各阶段 Tiling 不一致；未对齐尾块在核内逐元素搬到对齐地址 | 盲目扩大融合，而非削减瓶颈单元的工作量 |
| 损失函数 | 哪部分逐元素、哪部分归约？模式如何分派？ | 归约尾块 padding；指数溢出；低精度统计量 | 每个归约步骤重复搬同一数据 |
| 优化器 | **本快照无特征** | — | — |
| Resize/插值/采样 | 是坐标驱动的逐输出 gather，还是规则路径？是否在 Tiling 阶段选定？ | 热循环内反推坐标；边界处理混进加权循环；邻域点未合并 | 输出规模小时核利用率不足 |
| Shape/排布/拼接 | 需要片上重排，还是只需搬运？ | Kernel 内推导几何关系；同一队列被两条流共用 | 把重排与不重排路径塞进同一串行方案 |
| Foreach | **本快照无特征** | — | — |
| Mask/条件/过滤 | 输出长度静态，还是依赖数据？ | 动态长度输出缺两阶段 workspace；生产完成前读偏移 | 逐元素标量筛选 |
| Cast/类型转换 | 有哪些源/目标 dtype 与布局组合？是否适合表驱动分派？ | 运行期类型分支；重复生成常量；标量写入后缺顺序保证 | 标量逐元素转换 |
| Random | **本快照无特征** | — | — |
| 量化/反量化 | 量化轴是否为尾轴？每个 scale 的生命周期？ | scale/offset 生命周期与流式操作数混杂；假设所有 buffer 字节数相等 | 统计量/scale/Cast 每步重复搬运；bank 冲突 |

**表外族：** Matmul/GEMM/BMM、Convolution、注意力、整层结构、通信/通算融合不在本文件范围内（矩阵计算单元 / 跨卡通信，见第二部分开头的范围说明）。

**K23 注：** 该族在源表中 14/17 条标"A5 强相关=否"，另有 3 条标"是"，结论不一致。上表保留通用量化实现，不要当作 A5 平台的评分依据。

## 14. 把特征转成平台机制

评分地图提供的是证据，不是现成的杠杆。下表把特征类别映射到第一部分的机制类型与可能的失败类别。**它们都不意味着必须新增阶段。**

| 特征类别 | 可能的失败 | 可考虑的机制方向 | 机制示例 |
|---|---|---|---|
| 范式与路由 | `COMPILE-FAIL`、`ACCURACY` | §4 产物契约、控制流 | 要求设计阶段输出路由表；codegen 输出匹配分派；机械核对两份产物 |
| Tiling 与 buffer 预算 | `COMPILE-FAIL` | §4、§7、客户端工具 | 解析 Tiling 与 Kernel buffer 声明，把首个不一致字段反馈给产出阶段 |
| 硬件容量 | `COMPILE-FAIL`、`UNDER-PERF` | §7 | 扫描无法追溯到平台查询的容量与核数；要求 Tiling 说明推导依据 |
| 尾块、对齐与布局 | `ACCURACY` | §8 验证门禁 | 用算子自身用例测不能整除的 shape 与非连续输入；需要尾块时检查有无对应路径 |
| 精度计划 | `ACCURACY` | §2 技能、§8 | 要求设计阶段给出精度计划；核对窄 dtype 多步计算与尾块掩码 |
| 同步与确定性 | 间歇性 `ACCURACY` | §8、§6 | 首次精度失败或检测到多阶段、多核 Kernel 时，触发有界重复测试并附依赖边清单 |
| 流水与队列深度 | `UNDER-PERF` | §3 提示词、性能阶段 | 要求设计阶段说明瓶颈与重叠方案；按 Tiling 核对队列深度与执行顺序 |
| 分核策略 | `ACCURACY`、`UNDER-PERF` | §7、客户端工具 | 查尾块是否用实际余量、空闲核是否提前返回、小 shape 是否走对路由 |
| 封装层与注册 | `LOAD-FAIL` | §4 | 机械核对 `proto.yaml`、封装层 schema、注册入口之间的契约 |

**成本约束在这里尤其重要。** 源表共 422 条记录（本文件只取 vector 子集）。哪怕只把一部分变成每个算子必跑的检查，也可能用额外成本换有限的通过率收益，而目标函数未必认可这种交换。

按轨迹优先选一到两个占主导的失败类别，在最低成本层级实施：先静态检查再 NPU 运行，先用算子自身用例再谈阈值。所有检查都要有边界。

## 15. 常见误用

- **把评分细则直接抄进技能正文。** 大量文字规则既不可检查，又与阶段提示词争夺注意力。要么转成具体流程或检查机制，要么就别为"覆盖全面"而加。
- **把族级原则改写成具名算子的固定配方。** "遇到某个窗口归约算子就用这些常量"是记忆化；"先判断窗口能否放进片上，不能则流式处理，并从输出 tile 反推输入 tile"才是工程方法。
- **无条件使用 A5 特性。** 声明式调度、寄存器级路径、SIMT/SIMD 拆分、多维描述符都应先经平台查询确认，每条路径为不支持的平台保留回退。
- **混淆性能与精度。** 性能特征不能证明精度问题已解决，反之亦然。
- **为空白族补造结论。** 没有记录可查的族应明确写"证据缺失"。
- **让检查机制阻止产物生成。** 在 Kernel 生成之前就要求查七个维度、重复跑四次并做两轮 golden 比对，会把平台变成 `NO-ARTEFACT` 机器。检查应在可部署产物已存在之后进行，且不能以阻止产出为代价。
